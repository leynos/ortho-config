# Restore cognitive-complexity coverage for Windows-only Rust code (#738)

## Purpose

PR #737 replaced the workspace Clippy cognitive-complexity gate with Whitaker's
`macro_aware_cognitive_complexity` at a limit of 9. Whitaker runs only on the
Linux continuous-integration (CI) leg, and the Windows leg runs
`make lint-clippy` alone. Neither leg therefore scores code that exists only
under `#[cfg(windows)]`: the Linux run never compiles it, and the Windows run
no longer carries a complexity lint at all.

This plan restores that coverage without introducing a Windows Whitaker lane,
which the issue records as an accepted estate-wide trade-off.

## Outcome

Windows-only Rust code is scored by the same macro-aware cognitive-complexity
lint, at the same threshold, from the Linux CI leg. The mechanism, its
threshold, and its treatment of macro-generated branches are documented, and a
self-test demonstrates that an in-limit example passes while an over-limit
example fails.

## Background and evidence

### The gap

`dylint.toml` opts in to `macro_aware_cognitive_complexity` with
`max_complexity = 9`; `clippy.toml` records that Clippy no longer gates
complexity at all. `Makefile`'s `lint-whitaker` target is invoked from the
`Lint` step, which `.github/workflows/ci.yml` guards to
`matrix.platform == 'linux'`. The non-Linux leg runs `make lint-clippy`, which
is rustdoc and Clippy only.

Dylint lints run inside a rustc driver, so the lint sees whatever the compiler
is asked to compile. On Linux that is the host `cfg` surface; a
`#[cfg(windows)]` item is removed before any lint can run. The loss is total,
not partial.

### The decisive experiment

A probe crate carrying one `#[cfg(windows)]` function scoring 12 and one
scoring 2 was checked with Whitaker twice, at suite revision
`nightly-2026-05-28`.

- Host target: no diagnostics. The functions were not compiled.
- `--target x86_64-pc-windows-msvc`:
  `error: over_limit has a cognitive complexity of 12 (limit 9)` naming only
  the over-limit function, with the note
  `Branching generated by macro expansion is not counted.`

So the macro-aware lint, its threshold, and its macro handling all survive a
cross-target run unchanged. Cross-target checking needs only the target's
`rust-std`; `cargo check` does not link, so no Windows linker or software
development kit is required on the Linux runner.

## Decision

Extend the existing Whitaker invocation with a second `cargo check` pass at
`--target x86_64-pc-windows-msvc`, run from the Linux leg.

### Alternatives considered

| Option                                              | Verdict                                                                                                                                                                                                      |
| --------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Run Whitaker on the Windows leg                     | Rejected: the issue records the Linux-only Whitaker estate trade-off as accepted, and the installer stages Linux shared objects.                                                                             |
| Restore Clippy's `cognitive_complexity` for Windows | Rejected: PR #737 removed it because it scores after macro expansion, so `tracing` under the `log` bridge and `quote!` inflate it. Reinstating it would give Windows a different, noisier metric than Linux. |
| A bespoke source-parsing complexity script          | Rejected: a second metric to keep in step with the first, with no upstream maintenance.                                                                                                                      |
| Cross-target Whitaker pass on the Linux leg         | **Selected**: identical lint, identical threshold, identical macro handling, no new runner class.                                                                                                            |

### Threshold and macro handling

The threshold is 9, read from `[macro_aware_cognitive_complexity]` in
`dylint.toml`. Both passes read the same file, so the Windows pass cannot drift
from the Linux one. Branches a macro generated are not counted in either pass,
which the lint states in its own diagnostic note.

## Implementation

### 1. Makefile

Delivered as four Make targets, an installer-toolchain helper, the CI job that
runs them, and a probe crate.

- `WINDOWS_TARGET ?= x86_64-pc-windows-msvc` names the triple once.
- `lint-whitaker-windows` runs the suite against that target, assigning
  `STRICT_RUSTFLAGS` alone exactly as the host pass does.
- `install-whitaker-windows-target` and `check-whitaker-windows-target` add and
  verify the target's `rust-std` in Whitaker's own toolchain. The channel is
  read from `whitaker-installer install --dry-run`, because that toolchain is
  the installer's rather than the pin in `rust-toolchain.toml`. The split
  mirrors `install-build-tools` and `check-build-tools`: a gate reports a
  missing prerequisite instead of reaching the network itself.
- `check-windows-complexity-gate` runs the same command over
  `tests/fixtures/windows_complexity_probe`.

The Windows pass is deliberately **not** folded into `make lint` or
`lint-whitaker`, which the first draft of this plan proposed. It compiles the
whole workspace a second time for a target with no cache history, and the
`build-test` Linux leg is sized for disk rather than wall time; a separate
`lint-whitaker-windows` job keeps the required job's budget intact and makes a
failure name one surface instead of two. The host pass is therefore unchanged,
which is what keeps acceptance criterion four trivially true.

### 2. CI

A `lint-whitaker-windows` job on `ubuntu-latest` installs Whitaker through the
same pinned shared action as the required Linux leg, provisions the target's
`rust-std`, runs the pass, and then runs the self-test. `whitaker_install_test`
was widened from "exactly one install step" to "every install step, on a Linux
runner, through the pinned action", and the new
`windows_complexity_gate_test.py` holds the Makefile, the workflow, the
threshold and the fixture together.

### 3. Self-test

`tests/fixtures/windows_complexity_probe` is a standalone crate, deliberately
outside the workspace so `--all-features` cannot compile the over-limit
example. Every item is `#[cfg(windows)]`; the default build carries only an
in-limit example and must exit zero, and the crate's `over_limit` feature adds
an example that scores above the limit and must be reported.
`scripts/verify_windows_complexity_gate.py` runs both and reads the limit from
`dylint.toml` rather than repeating it.

Non-vacuity was demonstrated in both directions: at the Windows target the
over-limit example is reported at 11 against a limit of 9, and at the host
target it is not compiled at all, at which point the check fails and says so.

### 4. Documentation

`docs/developers-guide.md` gains "Windows-only code and the complexity gate",
the routing table gains a row, the tracing rule points at the new pass,
`dylint.toml` records that both passes read it, and `docs/repository-layout.md`
records the fixture's deliberate non-membership.

## Acceptance criteria

- [x] Windows-only code is scored in a CI complexity check.
- [x] The threshold (9) and macro-generated-branch handling are explicit and
      shared with the Linux pass.
- [x] A check demonstrates an in-limit example passes and an over-limit example
      fails.
- [x] Existing Linux Whitaker coverage is unchanged.
